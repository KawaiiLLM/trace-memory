# Ticket 01 — core/model, core/store, façade skeleton

Spec: .scratch/v1/spec.md (sections Modules, Run boundaries, Run record contract, Visibility rule, Schema). Glossary: CONTEXT.md. English only in the repo.

Deliver:
1. core/model: TypeScript types for Turn, ToolCall, Fact, FactRelation, Entry, EntryRevision, Run, Mark; shape validation functions for note output (batch array, categories, actors, event prefixes, `$n` handles, no `F`/`E` ids inside fact text, relation shape) and settle output (candidate handles `$e<n>`, categories, scopes, operations). Validation returns a list of problems; it never throws on model output.
2. core/store: `openStore(path)` on bun:sqlite creating the schema from the spec (all tables, FTS over facts and entries, the three indexes). Methods only for what note, settle, inject, compact, trace, search, mark need: sessions and projects (declare, merge with retroactive relabel), turns and tool_calls (append; ordinal per turn), facts with relations (append; handles resolved to ids inside the transaction), entries with revisions (new/edit/merge/archive as revisions; revision conflict → rejected operation returned, others commit), links, runs (every attempt, with request/response), marks, pending deliveries, watermarks, visibility query (global + project + this session's session entries). One transaction per committed run.
3. core/api: `TraceMemory(dbPath, runAgent, config)` with the method signatures from the spec; note/settle/compact/inject/trace/search/mark may throw NotImplemented for now except the store-backed reads needed by the tests.
4. Tests (bun test), driven through core/api and the store's public interface only: schema creates; global ids increase across sessions and projects; session id allocated only with the first assistant reply; `$n` resolution and invalid handle rejection; revision conflict rejection; merge relabel; visibility rule; run record written on failure. Use a temp file DB per test.

Constraints: no host SDK imports; no abstraction over SQLite; flat config object; no plugin or event machinery; keep it under ~900 lines excluding tests. Run `bun test` and `bunx tsc --noEmit` before reporting. Work sequentially; do not spawn subagents; if the chunk is too big, stop and report the split. Report: files, line counts, test results, and any spec ambiguity you had to resolve (state the choice).
