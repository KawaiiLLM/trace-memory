# 23c — Pi's line format with our addresses, a half/half split inside `B`, one marker, and `full` on the renderer

**Parent:** 23 — One entry view, two budgets (amendment 2026-09-09, "Line format and split"). Everything in the parent's "Implementation Decisions" that this ticket does not name stays binding: one renderer, `B` and `E`, the budget contract, tool parts yield before text, the host-registered result-text extractor, images and dropped structured data marked, no call ids and no native identity in the model-facing text, immutable versioned views, capacity error below the minima.

**Reference:** Pi's own compaction serializer (`core/compaction/utils.js` in the installed `@earendil-works/pi-coding-agent`: `[User]:`, `[Assistant]:`, `[Assistant tool calls]: name(k=JSON, …)`, `[Tool result]:` with a `[... N more characters truncated]` marker). Copy its line shape and its marker family; keep our addresses, our budgets and our head-and-tail cuts.

**What to build:** every source entry renders in Pi's line shape with the source address as the label, so a reader of Pi's summaries reads ours without learning a second format, and the Noter cites exactly the label it sees:

```
[T42#user]: 看一下最新的导出。
[T42#assistant]: Two things at once.
[T42#t3] bash(command="cd … && wc -l core/*/*.ts …", timeout=30)
[T42#t3] bash success: 47 core/api/index.test.ts
 218 core/api/index.ts
 …
[T42#t4] edit success: Edited /tmp/x.ts
[... 21 characters of details truncated]
```

Rulings (user, 2026-09-09), each binding verbatim:

1. **Line format.** A natural-text part is `[T<n>#user]: <text>` or `[T<n>#assistant]: <text>`. A tool-call part is one line, `[T<n>#t<k>] <name>(<key>=<JSON>, <key>=<JSON>)`, the arguments concatenated as `key=JSON.stringify(value)` in stored key order, so a value's boundary is never ambiguous (the per-key lines of 23a could be confused by a multi-line value containing `key: `). A tool-result part is `[T<n>#t<k>] <name> <status>: <text>`, the host-extracted text following the colon on the same line and continuing on the following lines as stored. A payload that is not a JSON object renders as `<name>(<raw>)`. Non-text blocks and dropped structured data keep their markers (rule 3).
2. **Short arguments whole, long arguments head and tail.** Inside `B`, arguments and result each take **one half** (superseding the parent's quarter / three quarters: measured on the real log, results were already cut in 573 of 835 calls at three quarters, while the quarter cut 218 of 337 bash commands; at `B = 300` the half split is 150 / 150 and totals 286K against 312K, −8%). A value that fits its fair share is rendered whole; a value that does not is cut **head and tail in equal halves inside its JSON string**, the marker standing between the two quoted halves: `command="python3 - <<'PY'\nfrom …"[... 1190 characters truncated]"…\nPY\nnode /tmp/probe.mjs"`. Fair shares among keys as in the parent (equal shares, remainders to the earliest keys, one return pass from short values). The original is fetched with `trace` and `full`, as before. **Boundaries (GPT review 2026-09-09):** a string value is cut on its raw code points and each half is JSON-encoded separately, so no escape sequence is ever split; any other value (array, object, number, boolean, null) renders as its compact JSON text and, when it must yield, is cut on that text head and tail with the same marker between — not valid JSON any more, but marked as such; a key that is not a plain identifier (`/^[A-Za-z_$][A-Za-z0-9_$]*$/`) renders JSON-quoted (`"a=\"x\", b"=1`), so `{"a=\"x\", b": 1}` can never read as two arguments.
3. **One marker, Pi's family.** Every omission in a view is `[... N characters truncated]` — text parts, argument values, result text, and the whole-part floor of a sealed call (`[T<n>#t<k>] bash(...)` followed by `[... N characters truncated]` when nothing of the arguments is kept). Dropped structured data is `[... N characters of details truncated]`; a non-text block is `[<type> omitted]` as today. The wordings `[omitted N characters]`, `[omitted N characters; middle not inspected]` and `[details omitted: N characters]` are deleted; the honesty clause "the omitted middle was not inspected" moves into the Noter prompt sentence once, instead of being repeated in every marker. The run audit's omission detection (the regex over the rendered view in Noting) is updated to the new marker family, and the entry audit still records every marker of every entry.
4. **`full` is the same renderer with no budget.** An explicit `trace` with `full` renders through the entry renderer's **unbounded** path and the **raw** result extractor (the stored string as is), so arguments, result text and `details` (edit diffs) appear whole under the same labels as every other view. **Read scope is unchanged (GPT review 2026-09-09):** `full` stays unrestricted — every native occurrence of the Turn's calls, whatever branch selected it, exactly as 17a rules ("shared-call fork results retain both originals through unrestricted full trace") and as 23b left it; the reader's `branch` narrows only the assembled read without `full`. The registered `trace` tool always passes the session's branch, so this is verified through the tool binding, not only the façade. **Unbounded means no budget machinery:** the unbounded path reuses the line formatting and skips cutting, allocation, the character-array split and every token measurement, so a `full` read of a large result copies strings as the deleted path did; `renderTrace` already shows each native occurrence of a call as its own entry, so the `multiple results` merge, the `tool=… status=… omitted=…` labels and the `input:` / `result:` blocks are deleted with `renderTurn`'s `full` path. `renderTurn` itself is deleted: Noting's head reply is rendered as the text part `[T<n>#assistant]: <text>` by the entry renderer (an entry-shaped value built from the Turn's assistant text, or the renderer's text-part function exported for it — the implementer chooses, and says which in the report). The 17a ruling that an unrestricted `full` trace retains both fork results stays pinned through `renderTrace`'s unbound path.
5. **Everything downstream of the bytes moves with them.** `ENTRY_VIEW_VERSION` changes; the compaction tier-2 title, the run audit's view version and profile, the Noter prompt sentence describing labels, markers and the split (hash moves; fork gate re-run against the updated parent request, never assumed), `docs/core.md` and `docs/pi.md` where they show the view, and every golden. Tier 2 keeps `B = 100`, `E = 1,000` (the half split makes it 50 / 50).
